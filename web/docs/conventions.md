# Web conventions

How the showcase site and the back office are structured and the practices
every change follows. Reviews check against this file.

## Structure

```
src/
├── proxy.ts            picks the zone from the host (site or back office)
├── app/                routes only: layouts, pages, error pages
│   ├── (site)/         showcase site, www.senami.fr
│   ├── admin/          back office, app.senami.fr (rewritten, never linked)
│   ├── layout.tsx      root: language, font, global styles
│   └── globals.css     Tailwind and the theme tokens
├── config/             environment contract (no state, no I/O)
├── core/               the API client, the zone routing
├── features/           the screens of a feature, one folder per feature
└── shared/             stateless building blocks, by technical kind
test/                   end-to-end tests (Playwright)
docs/                   this file, features/<area>/<feature>.md
```

| Folder      | Rule                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------ |
| `app/`      | Thin: a page reads its params, calls a feature, renders its components. No business logic. |
| `config/`   | Definitions only.                                                                          |
| `core/`     | Infrastructure every feature uses. Knows no feature.                                       |
| `features/` | A feature imports `core/` and `shared/`, never another feature.                            |
| `shared/`   | Stateless, importable anywhere, grouped by technical kind.                                 |

### Two zones, one app

`www.senami.fr` serves the showcase site and `app.senami.fr` the back office.
`src/proxy.ts` rewrites every back office request under `/admin` and adds
`X-Robots-Tag: noindex`; on the site host, `/admin` answers 404. So:

- a back office page lives in `app/admin/`, but its URL has no `/admin`:
  `app/admin/etablissements/page.tsx` is `app.senami.fr/etablissements`;
- links inside the back office never contain `/admin`;
- the session cookie is set by the API on the back office host only: the
  showcase site never sees it.

### Shared, by technical kind

```
src/shared/
├── components/ui/   shadcn/ui components (button, input, label...)
├── components/      other components used by several features
├── enums/           *.enum.ts   domain values: UserRole, SessionChannel...
├── hooks/           use-*.ts
├── types/           *.ts        types used by several features
└── utils/           pure functions: cn(), isRecord()
```

No folder named after a feature in `shared/`. Create a folder when its first
file arrives.

### A feature

```
src/features/<feature>/
├── components/   *.tsx           the feature's components
├── actions/      *.action.ts     Server Actions
├── api/          *.api.ts        calls to the API, through serverApi
├── schemas/      *.schema.ts     zod schemas of the forms
└── hooks/        use-*.ts
```

Only the sub-folders the feature uses, always under these names. The screens
of a feature are specified in `docs/features/<area>/<feature>.md` (see
[`CONTRIBUTING.md`](../../CONTRIBUTING.md#feature-work)); the spec links the
API spec it relies on, in `backend/docs/features/`.

## Server and Client Components

- Components are Server Components by default. `'use client'` only for state,
  effects, event handlers or browser APIs, and as low in the tree as
  possible: a form, not its page.
- Data is read in Server Components, through `serverApi`; never fetched in a
  `useEffect`.
- A Client Component receives plain serialisable props, never a function
  from the server nor a whole API object it does not display.

## Calling the API

- **From the server**: `serverApi` (`@core/api/server-api`) in Server
  Components, Server Actions and route handlers. It forwards the
  `senami_session` cookie and sends the back office `Origin`, which the API
  checks on every cookie-authenticated write.
- **Writes** go through Server Actions, which call `serverApi` and then
  `revalidatePath()` or `redirect()`.
- **From the browser**, when a call cannot go through the server: `/api/...`
  on the same origin, rewritten to the API by `next.config.ts`. Never the API
  host directly.
- The session token never reaches JavaScript: the cookie is `HttpOnly`, and no
  token goes into `localStorage`, `sessionStorage` or a client state.
- Types come from the API: `ApiSchemas['AuthUserDto']`
  (`@core/api/api-types`), generated by `pnpm api:types`. Never retype a DTO
  by hand.
- `serverApi.request()` returns the envelope (`{ data, meta? }`) and throws
  an `ApiError` otherwise. Branch on `error.code` (`TOTP_LOCKED`,
  `VALIDATION_FAILED`), never on `error.message`, which is for developers.
  `error.fields` holds the field errors of a 422: show them next to their
  field.
- A domain value from the API is compared to its enum
  (`user.role === UserRole.SUPER_ADMIN`), never to a string (ESLint rejects
  it). Enums mirror the backend ones, in `shared/enums/`.

## Forms

- react-hook-form with a zod schema (`@hookform/resolvers/zod`), in
  `features/<feature>/schemas/`.
- The client checks for comfort; the API decides. Always display the API
  field errors, even when the client schema passed.
- Every field has a visible `<Label>`; errors are linked with
  `aria-describedby` and `aria-invalid`.
- A submit button is disabled while pending and says so.

## User interface

- Components from [shadcn/ui](https://ui.shadcn.com), copied into
  `shared/components/ui/` and owned by the project:
  `pnpm dlx shadcn@latest add dialog` (aliases in `components.json`).
- Colours, radius and font are tokens in `globals.css`. Use the token classes
  (`bg-primary`, `text-muted-foreground`), never a raw colour. The palette is
  provisional until the brand colours arrive.
- Icons from `lucide-react`.
- Accessibility: semantic elements first (`button`, `a`, `nav`, headings in
  order), keyboard reachable, visible focus, contrast at least 4.5:1.

## Security and personal data

- Security headers are set for every response in `next.config.ts` (CSP,
  `frame-ancestors 'none'`, `nosniff`, HSTS over HTTPS). A new external
  origin (analytics, captcha) must be added to the CSP explicitly.
- The back office is never indexed: `noindex` header from the proxy and
  `robots` metadata in its layout.
- Never log, store in the browser or send to a third party a personal datum,
  a password, a code or a token. Fonts are served by the app (`next/font`),
  never from Google at runtime.
- No accident sheet content in the web app: the back office shows registers
  and statistics, never a sheet.

## Configuration

Variables are validated by `src/config/env.ts` when `next.config.ts` loads:
`dev`, `build` and `start` fail on a bad value.

- Server code reads `serverEnv` (`@config/server-env`, server-only).
- Browser code reads `publicEnv` (`@config/public-env`): `NEXT_PUBLIC_*`
  only, inlined at build time.
- A new variable is added to the schema, `.env.example`, the README and the
  Playwright `webServer.env`.

## Imports

- **Aliases** for anything outside the current folder, never `../` (ESLint
  rejects it):

  | Alias         | Folder          |
  | ------------- | --------------- |
  | `@app/*`      | `src/app/`      |
  | `@config/*`   | `src/config/`   |
  | `@core/*`     | `src/core/`     |
  | `@features/*` | `src/features/` |
  | `@shared/*`   | `src/shared/`   |

- `./` stays for a file of the same folder or below.
- No file extension: Next.js bundles the code (`moduleResolution: bundler`),
  unlike the backend which runs as native ESM.
- Aliases are declared once, in `tsconfig.json`; Vitest resolves them through
  `vite-tsconfig-paths`.

## Testing

| Kind       | Tool                     | File                                | Covers                                       |
| ---------- | ------------------------ | ----------------------------------- | -------------------------------------------- |
| Unit       | Vitest                   | `*.spec.ts`, next to the file       | pure functions, schemas, the API client      |
| Component  | Vitest + Testing Library | `*.spec.tsx`, next to the component | what the user sees and does                  |
| End-to-end | Playwright               | `test/*.e2e-spec.ts`                | the zones, then each feature against the API |

- Query by role and accessible name (`getByRole('button', { name: ... })`),
  not by class or test id.
- One test per behaviour and per failure case of the spec.
- No real personal data in tests.

## Language

Everything in the code is in English: identifiers, files, comments, test
names, commit messages, documentation. The text users read is in French and
lives in the JSX or in string values, never in an identifier. Typographic
apostrophes (`’`) in French text.

## Naming

| Element             | Case                                  | Example                                   |
| ------------------- | ------------------------------------- | ----------------------------------------- |
| Component           | `PascalCase` function                 | `LoginForm`                               |
| Component file      | `kebab-case.tsx`                      | `login-form.tsx`                          |
| Hook                | `useCamelCase`, file `use-*.ts`       | `useSessionTimer`, `use-session-timer.ts` |
| Server Action       | `camelCase` verb + `Action`           | `signInAction`, `sign-in.action.ts`       |
| API call            | `camelCase` verb                      | `fetchSessions()`, `sessions.api.ts`      |
| zod schema          | `camelCase` + `Schema`                | `loginSchema`, `login.schema.ts`          |
| Route segment       | `kebab-case`, French, as users see it | `/etablissements`, `/mot-de-passe-oublie` |
| Enum, member, value | as the backend                        | `UserRole.SUPER_ADMIN = 'super_admin'`    |
| Unit / e2e test     | `*.spec.ts(x)` / `*.e2e-spec.ts`      | `api-client.spec.ts`                      |

The rest of the TypeScript casing follows
[`backend/docs/conventions.md`](../../backend/docs/conventions.md#typescript),
enforced by the same ESLint rule.

## Code style

- No em dash anywhere.
- Comments are short and say what the code cannot.
- Prettier formats (including the Tailwind class order), ESLint checks.
  Never hand-format.

## Checks

Before committing and before opening a pull request:

```bash
pnpm format && pnpm lint && pnpm typecheck && pnpm test
pnpm test:e2e   # when a page, the proxy, next.config.ts or a feature flow changed
```
